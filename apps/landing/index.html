    02How it works

    Your code is the workflow.
    The history is the truth.

    async function orderSaga(ctx, order) {
  const saga = ctx.saga()
  try {
    await ctx.activity('reserveInventory', order)
    saga.add('releaseInventory', order)

    await ctx.activity('chargeCard', order)
    saga.add('refundCard', order)

    await ctx.sleep(4000)            // durable
    await ctx.child('fulfillment', order)
    await ctx.activity('sendConfirmation', order)
  } catch (err) {
    await saga.compensate()          // refund, release
    throw err
  }
}
    1. 1

      Record

      Every ctx.* call becomes an event in Postgres: scheduled, started, completed, failed, timer fired. No serialized stack to corrupt.

    2. 2

      Replay

      A worker re-runs your function from the top. Calls already in history return their recorded results instantly. The first call without one is where real work resumes.

    3. 3

      Resume

      Workers hold a lease they must keep renewing. If one dies, the lease expires, another claims the workflow at a higher epoch, and the dead worker's late writes are rejected.

    03What it does

    Everything a workflow needs
    to outlive its process.

    • replay

      Deterministic replay

      Divergence is detected and parked as a stuck workflow, never silently corrupted.

    • crash

      Crash recovery

      Leases, heartbeats, epoch fencing. Workers are real OS processes; the kill is a genuine SIGKILL.

    • time

      Durable timers

      ctx.sleep holds no worker while it waits. Any worker wakes it when it's due.

    • retry

      Retries

      Attempts, backoff, jitter and non-retryable errors per activity. Every attempt is an event.

    • saga

      Compensation

      Undo steps run in reverse as recorded, retried, idempotent activities.

    • flow

      Signals and children

      Park on a human approval, fan out child workflows, query live state.

    • ship

      Safe code changes

      ctx.patched() versions in-flight runs. A fuzzer finds hidden clock and RNG use.

    • see

      Observable

      History timeline, state inspector with a replay debugger, OpenTelemetry traces across workers.

    • scale

      Bounded history

      continueAsNew hands state to a fresh run so long loops never replay forever.

    04Use cases

    If it can't half-finish
    or run twice, it's a workflow.

    Reach for it when work takes more than a few seconds, touches more than one system, or would hurt if it stopped midway or repeated itself.

    • Checkout and order fulfilment

      Reserve stock, charge the card, ship, send the receipt. If shipping fails, refund and release stock automatically, in reverse order.

      activitysagachild workflow

    • Subscriptions and failed-payment recovery

      Retry a declined card on day 1, 3 and 7, then cancel. The schedule lives in the workflow, not in a cron table you have to babysit.

      sleepretries

    • Onboarding with human approval

      Create the account, then wait days for a manager to approve. The workflow just sits there, costing nothing, until a signal arrives.

      signalsleep

    • Reminders and trial expiry

      "Email them in 3 days unless they upgrade." One line of code, and it survives deploys and restarts.

      sleepsignal

    • AI and LLM pipelines

      A multi-step agent where every model call costs money. Finished steps are replayed from history instead of being paid for again after a crash.

      activityretries

    • Data pipelines and ETL

      Fetch, transform, load, with backoff on flaky sources. A job that dies at row 40,000 resumes there, and continueAsNew keeps long runs light.

      retriescontinueAsNew

    • Provisioning and rollbacks

      Create a database, a bucket, a DNS record. If step four fails, tear down one to three in reverse instead of leaving orphans.

      sagaactivity

    • Document and media processing

      Fan out one child workflow per file, wait for all of them, then assemble the result.

      child workflowretries

    Who it's for

    TypeScript backend teams

    You already run Postgres and have multi-step jobs that must not half-finish or repeat. You'd rather not stand up a new cluster just to get durability.

    Teams evaluating durable execution

    A small, readable engine to prototype against before committing to a bigger platform. The same ideas in about 1,200 lines.

    Anyone learning how it works

    Ten files. Read replay.ts, run the tests, kill a worker. The fastest way to really understand determinism, leases and idempotency.

    5. 5

      Write your own workflow

      Define workflows and activities, start one from your app, and run workers as separate processes (as many as you like).

      import { Registry, Store, Worker } from '@durable-flow/engine'

const store = new Store(process.env.DATABASE_URL!)   // any Postgres
await store.migrate()                                // creates its tables, safe to re-run

const registry = new Registry()
  .workflow('welcome', async (ctx, user) => {
    await ctx.activity('createAccount', user)      // recorded; retried on failure
    await ctx.sleep(24 * 60 * 60 * 1000)           // sleeps a day, holds no worker
    await ctx.activity('sendTips', user)
    return 'done'
  })
  .activity('createAccount', async (user, ac) => {
    // call your API here. Pass ac.idempotencyKey along so a retry can't double-apply.
  })
  .activity('sendTips', async (user, ac) => { /* ... */ })

// start one, e.g. from your signup handler
await store.createWorkflow({ id: `welcome-${user.id}`, type: 'welcome', input: user })

// run a worker, in its own process
await new Worker({ id: 'worker-1', store, registry }).start()
      Honest note on packaging. It isn't on npm yet. Today, add your workflows next to examples/ in the cloned repo, or copy packages/engine/src (10 files, about 1,200 lines) into your project. An npm package is the obvious next step.
    6. 6

      Use your own Postgres

      Point the store at any Postgres 14+ database (Neon, Supabase, RDS, local). Workers can run on any machine that can reach it; the database is the only shared state.

      terminal
      $ export DATABASE_URL=postgres://user:pass@host:5432/dbname

    The API at a glance

    ctx.activity(name, input, opts?)Run a side effect. Recorded, retried with backoff, given an idempotency key.
    ctx.sleep(ms)A durable timer. Survives restarts and holds no worker while it waits.
    ctx.waitForSignal(name)Pause until store.signal(id, name, payload) arrives, e.g. a human approval.
    ctx.child(type, input)Run another workflow and await its result.
    ctx.saga().add(undoActivity, input) as you go, .compensate() on failure. Runs undos in reverse.
    ctx.now() · random() · uuid()Deterministic replacements. Recorded once, identical on every replay.
    ctx.patched(id)Change workflow code safely while old runs are still in flight.
    ctx.continueAsNew(input)Hand state to a fresh run so long loops keep a short history.
    ctx.setQueryHandler(name, fn)Expose live workflow state for inspection.

    06Fine print

    Not magic.
    Here's what it isn't.

    Exactly-once execution

    At-least-once, plus idempotency

    If a worker dies after the side effect but before the result is recorded, the activity runs again. You get exactly-once effects only if the service you call honours the key. Flip the switch in the demo to see the alternative.

    Makes your code deterministic

    You keep that promise

    Workflow functions must not read the clock, call Math.random() or touch the network. Use ctx.now(), ctx.random() and activities. The fuzzer finds mistakes; it can't prove there are none.

    A Temporal replacement

    A working implementation of the idea

    One Postgres, polling workers, TypeScript only. No sharding, multi-region, multi-tenancy or auth, and none of the production hardening.

    Low-latency

    Built for seconds to days

    Each step is a database round-trip plus a replay. Great for business processes, wrong for request handlers.

    Free replay

    Linear in history length

    Long-lived workflows need continueAsNew to reset the history.

    Fire-and-forget

    Await everything that matters

    An activity you start but never await is dropped when the workflow ends.

    The contract

    1. Workflows are deterministic. Same history in, same commands out.
    2. Activities are idempotent. Use the key; assume you'll be called twice.
    3. The history is the truth. If it isn't an event, it didn't happen.
