    Start the workflow, then kill Worker A while a step's bar is amber. That's the window between a side effect happening and the engine recording it.

    Your code is the workflow.
    The history is the truth.

    async function orderSaga(ctx, order) {
  const saga = ctx.saga()
  try {
    await ctx.activity('reserveInventory', order)
    saga.add('releaseInventory', order)

    await ctx.activity('chargeCard', order)
    saga.add('refundCard', order)

    await ctx.sleep(4000)            // durable
    await ctx.child('fulfillment', order)
    await ctx.activity('sendConfirmation', order)
  } catch (err) {
    await saga.compensate()          // refund, release
    throw err
  }
}
    1. 1

      Record

      Every ctx.* call becomes an event in Postgres: scheduled, started, completed, failed, timer fired. No serialized stack to corrupt.

    2. 2

      Replay

      A worker re-runs your function from the top. Calls already in history return their recorded results instantly. The first call without one is where real work resumes.

    3. 3

      Resume

      Workers hold a lease they must keep renewing. If one dies, the lease expires, another claims the workflow at a higher epoch, and the dead worker's late writes are rejected.

    What it does

    Deterministic replay
    Re-execution from history. Divergence is detected and parked as a stuck workflow, never silently corrupted.
    Crash recovery
    Leases, heartbeats and epoch fencing. Workers are real OS processes, so the kill is a genuine SIGKILL.
    Durable timers
    ctx.sleep holds no worker while it waits. Any worker wakes the workflow when it's due.
    Retries
    Attempts, exponential backoff, jitter and non-retryable errors per activity. Every attempt is an event.
    Sagas
    Compensations run in reverse as recorded, retried, idempotent activities.
    Signals, children, queries
    Park on a human approval, fan out child workflows, read live state.
    Safe code changes
    ctx.patched() versions in-flight workflows. A fuzzer finds hidden clock and RNG use before you deploy.
    Observable
    History timeline, per-workflow state inspector with a time-travel replay debugger, OpenTelemetry traces across workers.
    Bounded history
    continueAsNew hands state to a fresh execution so long loops never replay forever.

    The fine print

    Durable-execution marketing oversells. Here is what this isn't.

    Not exactly-once execution

    Activities run at least once. If a worker dies after the side effect but before the result is recorded, the activity runs again. You get exactly-once effects only if the service you call honours the idempotency key. Flip the switch in the demo to see the alternative.

    Doesn't make your code deterministic

    Workflow functions must not read the clock, call Math.random() or touch the network. Use ctx.now(), ctx.random() and activities. The fuzzer finds mistakes; it can't prove there are none.

    Not a Temporal replacement

    One Postgres, polling workers, TypeScript only. No sharding, multi-region, multi-tenancy or auth, and none of the production hardening. It's a working implementation of the idea, built to learn from.

    Not for latency-critical paths

    Each step is a database round-trip plus a replay. Think seconds-to-days business processes, not request handlers.

    Replay cost grows with history

    Replay is linear in event count. Long-lived workflows need continueAsNew to reset it.

    No fire-and-forget

    An activity you start but never await is dropped when the workflow ends. Await everything that matters.

    The contract

    1. Workflows are deterministic. Same history in, same commands out.
    2. Activities are idempotent. Use the key; assume you'll be called twice.
    3. The history is the truth. If it isn't an event, it didn't happen.
