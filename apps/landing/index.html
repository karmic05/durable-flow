    Your code is the workflow.
    The history is the truth.

    export async function orderSaga(ctx, order) {
  const saga = ctx.saga();
  try {
    await ctx.activity('reserveInventory', order);
    saga.add('releaseInventory', order);

    await ctx.activity('chargeCard', order);
    saga.add('refundCard', order);

    await ctx.sleep(4000);                  // durable timer
    await ctx.child('fulfillment', order);
    await ctx.activity('sendConfirmationEmail', order);
  } catch (err) {
    await saga.compensate();                // refund, then release
    throw err;
  }
}
    1. 1

      Record

      Every ctx.* call becomes an event in Postgres: scheduled, started, completed, failed, timer fired. Nothing else is stored. There is no serialized stack to corrupt.

    2. 2

      Replay

      When a worker picks the workflow up, it re-runs your function from the top. Calls already in history return their recorded results instantly. The first call without a recorded result is where real work resumes.

    3. 3

      Resume

      A worker holds a lease it must keep renewing. If it dies, the lease expires, another worker claims the workflow with a higher epoch, and the dead worker's late writes are rejected by fencing.

    What it does

    • Deterministic replay

      Re-execution from history, with non-determinism detected and surfaced as a stuck workflow rather than silent corruption.

    • Crash recovery

      Leases, heartbeats and epoch fencing. Workers run as real OS processes, so the demo's kill is a genuine SIGKILL.

    • Durable timers

      ctx.sleep survives restarts and holds no worker while it waits. The workflow parks and any worker wakes it.

    • Retries with backoff

      Per-activity policy: attempts, exponential backoff, jitter, non-retryable error types. Every attempt is an event.

    • Sagas

      Register compensations as you go; on failure they run in reverse as recorded, retried, idempotent activities.

    • Signals, children, queries

      Park on a human approval, fan out child workflows, and read live workflow state with queries.

    • Safe code changes

      ctx.patched() versions in-flight workflows, and a determinism fuzzer catches hidden clock and RNG use before you deploy.

    • Observable

      A history timeline, a per-workflow state inspector with a time-travel replay debugger, and OpenTelemetry traces that follow a workflow across workers.

    • Bounded history

      continueAsNew hands state to a fresh execution so long-running loops never replay forever.

    What it doesn't do

    Durable-execution marketing tends to oversell. Here is the fine print, stated plainly.

    It is not "exactly-once execution"

    Activities run at least once. If a worker dies after the side effect but before the result is recorded, the activity runs again. What you get is exactly-once effects, and only if the thing you call honours the idempotency key the engine hands you. The demo above has a switch that shows what happens when it doesn't.

    It does not make your code deterministic

    Workflow functions must not read the clock, call Math.random(), or touch the network directly. Use ctx.now(), ctx.random() and activities. The fuzzer helps find mistakes; it can't prove their absence.

    It is not a Temporal replacement

    One Postgres database, polling workers, TypeScript only. No sharding, multi-region, multi-tenancy, auth, rate limiting per namespace, or years of production hardening. It is a working implementation of the idea, built to learn from and to demo.

    It is not for latency-critical paths

    Each step is a database round-trip plus a replay. Think seconds-to-days business processes, not request/response handlers or sub-millisecond work.

    Replay cost grows with history

    Replay is linear in event count. Long-lived workflows need continueAsNew to reset history. The benchmark page shows where the curve bends.

    Fire-and-forget isn't supported

    An activity you start but never await is dropped when the workflow finishes. Await everything that matters.

    The contract

    The engine keeps its half of the bargain if you keep yours.

    1. Workflows are deterministic. Same history in, same commands out.
    2. Activities are idempotent. Use the key; assume you will be called twice.
    3. The history is the source of truth. If it isn't an event, it didn't happen.
